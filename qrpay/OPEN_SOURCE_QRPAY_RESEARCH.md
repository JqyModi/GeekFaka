# 个人二维码收款系统开源方案调研

更新时间：2026-04-21

## 先说结论

如果你的目标是：

- 个人收款码
- 自动回调
- 尽量免签
- 优先免挂

那么当前可选路线基本只有两类：

1. `V免签` 这类通知监听方案
2. `Jeepay` 这类官方通道聚合网关方案

其中：

- 如果你坚持用个人微信/支付宝收款码，`V免签` 这一类最接近你的目标，但本质上不是“真免挂”，只是可以用安卓备用机或模拟器低成本挂机。
- 如果你真正优先的是“免挂 + 稳定 + 自动回调 + 可长期维护”，应转向 `Jeepay` 这一类官方通道方案，但这条路通常不再是“个人静态收款码免签”。

## 关键判断

### 1. 真正的“免挂个人码”基本不现实

开源世界里，个人二维码收款要做到自动回调，主流做法仍然是：

- 监听手机通知
- 监听店员到账消息
- 安卓辅助服务/通知使用权
- 安卓备用机或模拟器常驻

也就是说，很多项目宣传“免签”，但并不等于“免挂”。

### 2. “源支付”目前更像商业授权产品，不适合作为纯开源首选

我没有找到一个当前公开、主流、持续维护的 GitHub 开源主仓库可作为你的首选基础。

当前官网信息更偏向：

- 购买源码授权
- 官方演示
- 付费文档和服务

所以它不适合你这个“基于 GitHub 开源方案自己搭建”的前置条件。

## 候选方案

### A. `szvone/vmqphp`

仓库：

- GitHub: <https://github.com/szvone/vmqphp>
- 监控端 APK: <https://github.com/szvone/vmqApk>

适合度：`最高`

原因：

- 就“个人二维码收款 + 自动回调”这个目标来说，它是最成熟、最广为人知的一类开源方案。
- README 明确支持支付宝、微信到账通知监听。
- README 明确支持店员通知、安卓备用机、模拟器挂机。

实际技术路线：

- 用户扫码支付
- 手机收到微信/支付宝到账通知
- 监控端监听通知
- 推送到服务端
- 服务端按金额匹配订单并触发回调

优点：

- 开源成熟，社区认知度高
- 个人开发者场景匹配度高
- 有现成服务端和监控端
- 自动回调链路清晰

缺点：

- 不是“真免挂”
- 依赖安卓通知监听兼容性
- 金额匹配存在天然局限，订单设计要避碰撞
- 不适合高并发、多商户、强风控正式商用

适合你的结论：

- 如果你要尽快搭出一套“自己能用”的个人收款系统，优先从它开始。
- 推荐形态是：`V免签服务端 + 安卓备用机/模拟器 + 你自己的业务回调层`

### B. `jeequan/jeepay`

仓库：

- GitHub: <https://github.com/jeequan/jeepay>
- 文档: <https://doc.jeequan.com/#/integrate/open>

适合度：`长期最佳，但不属于个人码免签路线`

原因：

- 这是目前仍然活跃、工程化最完整的开源支付系统之一。
- 支持微信支付、支付宝、云闪付官方接口。
- 支持多商户、聚合码、回调、退款、渠道管理。

优点：

- 真正的支付网关架构
- 最近仍在持续维护
- 自动回调、订单、退款、渠道管理都完整
- 适合以后扩展成正式支付中台

缺点：

- 需要官方支付通道或服务商资源
- 对“个人二维码免签”帮助有限
- Java + 多组件，部署复杂度高

适合你的结论：

- 如果你能接受从“个人收款码”升级到“正规支付通道”，它才是最稳的底座。
- 如果你的优先级是“免挂第一”，那应该优先考虑这条路，而不是继续追逐个人码免挂。

### C. `zengxiang1/epay-go`

仓库：

- GitHub: <https://github.com/zengxiang1/epay-go>

适合度：`可关注，不建议直接作为主方案`

特点：

- Go + Gin + PostgreSQL + Redis + Vue 3
- 项目很新，结构轻量
- README 展示了统一下单、后台、商户中心、订单/退款/结算流程

优点：

- 技术栈相对现代
- 比 Jeepay 轻
- 适合读代码或做二开参考

缺点：

- 体量小，社区和验证程度远不如 Jeepay / V免签
- 当前更像示例项目或早期项目
- 不适合直接作为你第一套生产基础设施

适合你的结论：

- 可以参考其 Go 实现思路
- 不建议作为你的首选落地方案

## 不建议作为首选的方向

### “源支付 / Ypay Plus”

当前观察结果：

- 官网主打正版授权和付费购买
- 更像商业产品
- 不符合“优先 GitHub 开源方案自建”的要求

结论：

- 不作为这次首选

### 只追求“免挂”的个人码黑科技方案

问题：

- 很多方案不可持续
- 容易依赖特定安卓版本、特定客户端版本或 Hook
- 长期维护成本高

结论：

- 不建议一开始就走这条路

## 我的推荐排序

### 方案 1：先落地能跑的版本

选择：

- `szvone/vmqphp`
- `szvone/vmqApk`

部署建议：

- Linux 服务器部署服务端
- 安卓备用机优先，其次模拟器
- 微信/支付宝使用店员通知模式
- 你自己的业务系统只对接它的回调接口

适用场景：

- 个人站
- 小流量
- MVP
- 验证业务闭环

### 方案 2：后续升级到正规免挂架构

选择：

- `jeequan/jeepay`

适用场景：

- 想长期运营
- 不想被挂机方案卡死
- 希望更稳定的回调和订单管理

### 方案 3：把 Go 版做成你自己的轻量系统

选择：

- 参考 `epay-go`
- 但不要直接无脑上线

适用场景：

- 你准备自己掌控代码
- 接受前期补功能
- 后面可能只保留最小支付闭环

## 对你当前项目最现实的建议

你现在已经建了 `qrpay` 目录，如果目标是尽快开始，我建议分两步：

1. 先基于 `V免签` 跑通一条完整闭环
2. 再评估是否迁移到 `Jeepay` 或官方服务商通道

第一阶段要验证的不是“完美免挂”，而是：

- 下单是否稳定
- 回调是否可靠
- 金额去重策略是否足够
- 订单超时和补单机制是否清晰
- 备用机/模拟器是否稳定在线

## 需要你接受的现实约束

- 个人码免签方案，核心风险不在代码，而在通道稳定性和通知兼容性。
- 你越想“免挂”，就越接近需要正规商户通道，而不是个人二维码方案。
- 所以“个人码 + 自动回调 + 真免挂 + 长期稳定”这四项通常不能同时满足。
